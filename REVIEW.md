# Ревью исходного API бронирования

Ревью относится к `app/Http/Controllers/BookingController.php` в исходном коммите `c68fb60`. Номера строк относятся к этой версии. [Исходный контроллер](https://github.com/andreygrigorasch/rcsi-science/blob/c68fb6079ea64c84f75cf7b374260b7ad29d3353/app/Http/Controllers/BookingController.php)

## Создание и отмена брони

| Серьёзность | Место | Проблема и последствия | Исправление |
| --- | --- | --- | --- |
| critical | `store`, строки 23–26 | `room_id` и обе даты подставляются прямо в SQL. Клиент с действующим токеном может изменить условие запроса, а некорректное значение может вызвать `500`. | Проверять входные данные и передавать значения через параметры Query Builder. |
| critical | `destroy`, строка 47 | Запись ищется только по ID. Любой пользователь с действующим токеном может удалить чужую бронь. | Ограничить удаление по ID и владельцу одним запросом. Для чужой и отсутствующей брони возвращать `404`. |
| major | `store`, строка 37 | `Booking::create($request->all())` принимает клиентский `user_id`, поскольку модель разрешает массовое присваивание этого поля. Бронь можно записать на другого пользователя. | Создавать бронь через связь текущего пользователя и передавать только проверенные поля. |
| major | `store`, строки 23–37 | Отсутствующие поля, неизвестная комната, неверная дата и слишком длинный заголовок могут привести к `500`. Порядок границ, длительность и сетка четвертей часа не проверяются. | Проверять поля до записи, валидировать обе границы и возвращать `422` с ошибками по полям. |
| major | `store`, строки 32–34 | Проверяется только час начала в смещении клиента. Бронь 15:45–16:15 при `+03:00` проходит проверку, хотя в Новосибирске это 19:45–20:15. | Переводить обе границы в пояс офиса. Проверять, что бронь целиком лежит в пределах 09:00–20:00 одного местного дня. |
| major | `store`, строки 25–26 и 37 | Колонки `timestamp` хранят дату без смещения. PostgreSQL отбрасывает смещение при сравнении литералов с этими колонками. Интервалы 10:00–11:00 при `+03:00` и 12:00–13:00 при `+05:00` обозначают один слот, но могут пройти как разные. | Приводить обе границы к UTC перед сравнением и записью. Для восстановления потерянных смещений старых записей нужен первичный источник. |
| major | `store`, строки 25–26 | Условия `<=` и `>=` считают 10:00–11:00 и 11:00–12:00 пересекающимися. | Использовать полуоткрытые интервалы. Пересечение есть при `existing.start < new.end AND existing.end > new.start`. |
| major | `store`, строки 23 и 37 | Проверка и вставка выполняются отдельно. Два запроса могут увидеть один свободный слот и оба создать бронь. | В одной транзакции блокировать строку комнаты, затем проверять пересечение и сохранять бронь до освобождения блокировки. |

## Чтение и аутентификация

| Серьёзность | Место | Проблема и последствия | Предлагаемое исправление |
| --- | --- | --- | --- |
| major | `today`, строка 55 | `today()` определяет дату по часовому поясу приложения, UTC. В 00:30 в Новосибирске запрос ещё выбирает предыдущую дату. | Получить границы местного дня в поясе комнаты, привести их к UTC и искать записи, пересекающие этот диапазон. |
| minor | Аутентификация без `Accept: application/json` | Анонимный запрос может получить `500`, поскольку middleware пытается разрешить отсутствующий маршрут `login`. | Возвращать JSON с `401` для неаутентифицированных API-запросов и проверить случай без заголовка. |
| minor | `today`, строки 56–59 | Обращение к `$b->user` после загрузки списка может вызвать отдельный SQL-запрос на каждую бронь. | Загрузить авторов заранее через `with('user')`. |
| minor | `today`, строки 54–59 | Порядок результатов не задан. Поле `time` объединяет обе даты в строку без явного смещения, что затрудняет обработку на стороне клиента. | Сортировать по началу и ID. Возвращать даты отдельными полями ISO 8601 со смещением. |
| minor | `index`, строки 16–18 | При одинаковом `starts_at` порядок записей при пагинации не определён. Один пользователь может забронировать разные комнаты на одно время. | Добавить сортировку по ID как второму ключу. |

## Корректное поведение исходника

- `auth:sanctum` требует аутентификации для API. Для операций над отдельной бронью дополнительно нужна проверка владельца.
- `index` ограничивает выдачу текущим пользователем. В `orderByRaw('starts_at DESC')` используется постоянное выражение без пользовательского ввода.
- `today(Room $room)` использует штатную привязку модели к маршруту. Канал `bookings` объявлен в `config/logging.php`.
